## Implemented and verified

All code is under lab/, using the pinned Go 1.27.2 module. Checker/provider business logic uses the standard library; the API/controller adapter adds controller-runtime v0.25.1 and Kubernetes libraries v0.37.0. The reservation workflow pins Temporal Go SDK v1.50.0.

- health.go: HostResult. health_sequential.go: CheckHostsSequential. health_concurrent.go: bounded CheckHosts, single collector, draining and joining on cancellation. Shared and concurrency-specific tests cover mixed outcomes, cancellation, actual overlap/bounds, invalid limits, and waiting for uncooperative checks.
- provider.go: fixed in-memory endpoint health/delay fixtures with cancelable waiting. examples/fleet: host-local and whole-batch deadlines. Tests cover mixed results, unknown host, cancellation, and configuration ownership.
- allocation.go: separate mutable SimulatedAllocator inventory, UID-owned hosts, atomic (UID, slot) EnsureHost, and owner-scoped repeatable ReleaseHosts. Released UIDs reject delayed allocations. Health fixtures and allocation inventory are not integrated yet.
- imaging.go: ImageRequest/ImageJob, EnsureImageJob, GetImageJob, and explicit simulated CompleteImageJob on the same provider. Atomic (OwnerUID, OperationID) lookup/creation and unchanged host/image parameters; ownership/fencing share the allocator mutex. Status observes Done; repeatable completion may arrive after cleanup even though closed owners cannot ensure/poll. Records remain as history. Unit tests cover lost-ID recovery, 20 concurrent duplicates, changed parameters, owner/operation isolation, invalid/canceled/unowned calls, completion persistence/retries, and late completion after cleanup. No real imaging process runs.
- reconcile.go: plain-Go ReconcileHosts discovers allocations, fills missing slots, and reports observations. Discovery failure stops allocation; scale-down is explicitly unsupported. It is not a Kubernetes controller adapter.
- Fault tests cover discarded status, lost allocation response, concurrent duplicate requests, owner isolation, invalid/canceled calls, repeated cleanup, and concurrent/late allocations after cleanup.
- examples/reconcile demonstrates two existing hosts, third allocated with discarded report, retry preserving three identities, cleanup retry leaving zero hosts, and rejection of delayed provisioning. examples/slices remains available as a reference.
- api/v1alpha1 and generated CRD: namespaced GPUCluster with immutable nodeCount (0–100), allocated host IDs/slots, observed generation, and standard conditions keyed by type. GPU class/location and readiness are deferred; allocation status does not claim health.
- controller/gpucluster_controller.go: finalizer persistence/removal with optimistic patches, deletion before allocation, UID-scoped cleanup, status writes only when changed, and SetupWithManager watching GPUCluster. Successful allocation passes request another check after configurable PollInterval (default 30s), including converged no-ops; errors use runtime backoff. Finalizer writes queue the next pass through the watch.
- Allocation condition: True/HostsAllocated after successful reconciliation; Unknown/ProviderError after a provider failure while preserving last-known count/IDs and their top-level observed generation. Condition observedGeneration records the current attempt. Standard helper preserves other conditions and avoids transition-time churn. Provider and status-write errors are joined for retry/diagnosis. No False, deletion, or Ready condition yet.
- Makefile: pinned code generation and native envtest setup. API tests cover protection-before-allocation, convergence, real metadata conflict preserving another finalizer, cleanup outage/retry and owner isolation, lost finalizer/status writes with a fresh reconciler, and input/spec-change validation. All spec changes are rejected in this increment, a stricter temporary policy than the eventual curriculum.
- provisioning/workflow.go and activities.go: ProvisionCluster runs one ReserveHosts activity using unchanged ClusterUID/NodeCount; the activity reuses ReconcileHosts and stable provider keys. Teaching settings: 5s StartToClose, 30s ScheduleToClose, 3 attempts with bounded backoff. Invalid inputs, released UIDs, and unsupported scale-down are non-retryable; partial allocations are not automatically compensated.
- provisioning/workflow_test.go: real SDK in-process suite and real simulated allocator, with response faults. Lost response plus stale discovery yields two attempts, the original first host, and exactly three allocations. Persistent transient failures stop after three attempts; invalid inputs make no provider calls; released-owner and scale-down rejection stop after one attempt, preserving inventory. These tests need no Temporal service and do not prove history replay or worker restart.
- provisioning/imaging.go: separate ImagingActivities.EnsureImage and consumer-side ImageProvider interface. Idempotent ensure on each attempt, heartbeat job/host details after observations, Done completion, 1s default/configurable poll delay selected against ctx.Done, and provider context propagation. Permanent request/ownership errors are non-retryable; read errors return to retry policy. No extra heartbeat goroutine or checkpoint restore. SDK tests cover three-poll completion, repeated heartbeat calls before batching, a real two-attempt lost-response retry of the original job, wait/read cancellation, provider errors, and release during polling. The image workflow used for retry tests is test-only.
